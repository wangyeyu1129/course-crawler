## 设计与职责

`crawler/snapshots.py` 只负责精确字节归档和完整性检查；不依赖网络、DOM、课程业务或 SQLite。
`crawler/storage.py` 决定课程结果导出的保存顺序；parser 仍只返回课程数据。
`crawler/runner.py` 在统计中返回 snapshot 路径，方便找到本轮对应历史内容。
自定义输出目录无需新配置：历史目录由输出文件位置和 stem 推导。

采用内容寻址：文件名为完整 SHA-256，字节内容相同则复用；不同则新增。
优点是重复恢复或重复导出不额外复制大文件，且文件名可以校验内容。
代价是文件名不显示时间，也不记录 parser 版本；本版通过运行日志记录统计与快照路径，
版本库保留本次交付代码与数据。未引入数据库快照索引、元数据文件或自动清理策略。
JSON 的格式变化也会产生新版本，这是保存精确历史字节的预期行为。

## 保存顺序与故障行为

1. 将新 JSON 写到临时文件并 flush/fsync；序列化失败不会动当前文件。
2. 当前文件存在时，先保存其精确字节快照，包括原有缩进和 Unicode 表示。
3. 保存新结果快照；已存在同名文件时比较字节，发现损坏则报错，绝不静默覆盖。
4. 最后用 os.replace 发布新的当前文件。

快照先写临时文件，再以排他 link 发布，避免暴露半写文件或覆盖已有版本。
归档临时文件与当前输出各自持有独立 inode，避免直接编辑当前文件连带修改历史。
归档失败时停止发布，原有当前文件保留；当前文件发布失败时，旧文件和已写快照仍可检查。
历史与当前文件不是跨文件事务：中断可能留下已归档但尚未发布为当前文件的新快照，这不会损坏旧历史。
临时文件在可处理异常时清理，强制终止可能留下点号前缀的临时文件。
快照按应用约定只写一次，不是文件系统权限层面的不可修改备份；人工删除和编辑不受此机制阻止。

## 测试证据

本阶段新增 11 个测试方法，并扩展实际 runner 回归测试。

| 范围 | 验证行为 |
| --- | --- |
| 基础导出 | 首次导出、Unicode/None 往返、空数组、SHA-256 与字节一致 |
| 历史保留 | 首次更新前已有文件归档、修改后新旧并存、相同内容复用 |
| 独立性 | 直接编辑当前文件不影响历史，inode 不同 |
| 故障 | 归档失败保留旧文件、已有快照损坏时停止、最终替换失败保留历史 |
| 原子发布 | 临时归档失败清理、同内容并发发布可安全复用 |
| 序列化 | 非 JSON 数据失败，不改旧文件，不创建无效历史 |
| 应用回归 | 分批抓取后旧快照不变；完成后恢复复用同一快照 |

## 范围说明与后续建议

按用户给出的第一版格式，这里的 Raw Data 是**解析结果 JSON**。
可以查看 parser 过去输出了什么，但不能据此离线重现 HTML 到字段的提取过程。
如下一阶段需要同一网页分别运行旧、新 parser，应由 HTTP/持久化层增加原始 HTML 快照，
parser 不应承担文件命名、归档或网络读取职责。

快照包含所有已成功课程；分批运行和失败运行也能导出，不能仅凭文件存在判断全目录完成。
历史副本有存储成本，目前按内容去重且不自动删除，适合第一版手工审查。
已有 POSIX 平台约束沿用 Phase 3；没有新增依赖。
